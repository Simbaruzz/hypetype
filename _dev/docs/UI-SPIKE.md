# hypetype UI Spike — прототип нового редактора (нативный AHK v2)

Экспериментальное ТЗ. Цель — **не** выпустить фичу, а получить ответ на один вопрос: *насколько близко нативный Win32/AHK v2 Gui может подойти к дизайну macOS-редактора (KeyboardEditorView2), и достаточно ли этого для прода.* Результат спайка — работающий прототип + скриншоты + вердикт владельца. Код пишется так, чтобы при положительном вердикте стать боевым модулем без переделки.

Референс дизайна: macOS-версия `KeyboardEditorView2.swift` (реалистичная клавиатура, тёмная тема, кейкап = Shift-символ сверху + основной символ снизу, широкая клавиша «ТИПОГРАФ» на месте Backspace, попап правки клавиши). Сюда переносим **структуру и UX**, честно принимая визуальные компромиссы натива (см. §4).

---

## 1. Рамки спайка

**Делаем (Стадия 1):** окно редактора-клавиатуры + попап правки клавиши. Работают против настоящего `Config` (реальные чтение и сохранение раскладки).

**Опционально (Стадия 2, только после вердикта по Стадии 1):** окно настроек типографа со скроллом (вендорный ScrollableGui).

**НЕ делаем:** интеграцию в трей-меню и hypetype.ahk; правки движка, input.ahk, registry.ahk; WebView2; GDI+/owner-draw рисование; конфиг-вотчер; никаких изменений существующего `editor.ahk` (старый редактор живёт нетронутым до вердикта).

## 2. Организация кода

- Ветка: `ui-spike`.
- Новые файлы: `src/editor2.ahk` (окно+попап) и `src/ui-preview.ahk` — отдельная точка входа: `#Include config.ahk` + `#Include editor2.ahk`, `Config.Load()`, открыть окно. Запуск интерпретатором, без компиляции.
- `editor2.ahk` общается с данными **только** через существующий API `Config` (`GetKey/SetKey/Keys`). Никаких собственных структур раскладки и копий таблицы клавиш — источник истины один.
- Коммит после каждого работающего шага (каркас окна → ряды клавиш → подписи из Config → клики → попап → сохранение → DPI).

## 3. Спецификация окна

### 3.1 Раскладка клавиатуры (адаптация мака под PC)

Пять рядов, сетка на юнитах (базовый размер клавиши `kUnit` ≈ 56px при 100% DPI, зазор ≈ 6px; итоговые размеры подобрать по референс-скриншоту мака):

1. `` ` `` · 1…0 · `-` · `=` · **ТИПОГРАФ** (широкая, на месте Backspace, с подписью-иконкой ⌫)
2. Tab (декор) · Q…P · `[` `]` · `\`
3. CapsLock (декор) · A…L · `;` `'` · Enter (декор; узкий «маковский» Enter допустим — решение владельца)
4. Shift (декор, широкая) · Z…M · `,` `.` `/` · Shift (декор, широкая)
5. Ctrl · Win · Alt (декор) · Space (флекс-ширина, mappable!) · **Alt (подсвеченный — это хайп-клавиша)** · Win · Ctrl · кластер стрелок (декор) — PC-нижний ряд вместо ⌘⌥

Роли клавиш как на маке: mappable (48 клавиш из таблицы FORMAT.md §5, кликабельны), decor (модификаторы, некликабельны, приглушены), typograph (клик — пока заглушка-tooltip «типограф работает по RAlt+⌫»), info (клавиша ⓘ — текст-подсказка), подсвеченный правый Alt.

### 3.2 Кейкапы: рекомендуемая техника

Нативные Button не умеют ни цвет текста, ни двухэтажные разноцветные подписи — **кнопки не использовать**. Кейкап собирать из **Text-контролов**: Text с тёмным BackColor как «тело» клавиши + два Text-слоя подписей (верхний — Shift-символ, приглушённый/акцентный цвет; нижний — основной символ, белый). Text-контролы поддерживают и цвет текста, и фон, и событие Click — этим достигается двухцветность, которую я считал недостижимой у кнопок. Скруглений не будет — плоские прямоугольники, это принятый компромисс (см. §4). Ховер — опционально: подмена BackColor по OnMessage WM_MOUSEMOVE; если окажется мерцающим или дорогим — выбросить, не упираться.

### 3.3 Тёмная тема

- Тёмный заголовок окна: DWM-атрибут `DWMWA_USE_IMMERSIVE_DARK_MODE` (DllCall DwmSetWindowAttribute, значение 20, с фолбэком 19 для старых сборок Win10).
- `Gui.BackColor` — тёмно-серый фон в тон маку (~`0x121212`).
- Шрифт: Segoe UI (системный), размеры подписей по референсу; для символов на кейкапах пробовать «Segoe UI Symbol» как фолбэк-стек, если базовый шрифт теряет глифы.
- Подписи: основной символ — белый, Shift-символ — приглушённый серый или фиолетовый акцент (~`0xB873FF`) — попробовать оба, показать на скриншотах.

### 3.4 Отображение символов на кейкапах

Портировать логику мака (`displayGlyph`): невидимые символы показываются подстановками (пробел `␣`, nbsp `⍽`, комбинирующая диакритика на носителе `◌`), длинные последовательности — первые 2–3 символа + `…`. Логику взять из спеки FORMAT.md §6 (та же, что для автокомментариев) — если она уже реализована в `config.ahk` для комментариев, переиспользовать, не дублировать.

### 3.5 Попап правки клавиши

Отдельное маленькое тёмное окно (owner — окно редактора, модальность через Disable owner'а): заголовок с именем клавиши, два поля ввода (Edit-контролы: «с Alt+Shift», «с Alt») с живыми символами, кнопки «сохранить»/«отмена». Сохранение → валидация как в текущем editor.ahk (≤32 кодпоинтов, без переводов строк) → `Config.SetKey()` → обновить подписи кейкапа. Тёмные Edit-контролы — попробовать `+Background` тёмный + светлый текст; если Edit упрётся в белое нутро — оставить светлые поля, зафиксировать скриншотом (это один из вопросов эксперимента).

### 3.6 DPI

Все размеры — через множитель от `A_ScreenDPI/96` (как в v1). Окно нерастягиваемое (`-Resize`). Обязательная проверка на 100/125/150%.

## 4. Принятые заранее компромиссы (не «чинить», не эскалировать)

1. Эмодзи на кейкапах — **монохромные** (GDI не умеет цветные глифы). Не пытаться обходить.
2. Скруглений углов нет — плоские кейкапы.
3. Анимаций нет.
4. Точного пиксель-паритета с маком нет — цель «опрятно и той же структуры», не «неотличимо».

Если в ходе работы кажется, что компромисс можно снять только через owner-draw/GDI+/WebView — **не делать**, записать в отчёт как ограничение. Это спайк про границы натива, выход за натив — отдельное решение владельца.

## 5. Вопросы эксперимента (на них отвечают скриншоты)

1. Тёмное окно с Text-кейкапами — выглядит опрятно или «колхоз»?
2. Монохромные эмодзи на клавишах — терпимо?
3. Двухцветная подпись через слои Text — работает? Кликается всей площадью?
4. Тёмные Edit-поля в попапе — получились или остались белыми?
5. 125%/150% DPI — сетка не разъехалась?
6. Ховер — работает без мерцания или выброшен?
7. (Стадия 2) ScrollableGui — плавно ли, мерцает ли?

## 6. Критерий выхода

Владелец кладёт рядом скриншот мака и скриншоты прототипа (100% и 150% DPI) и выносит один из вердиктов: **(a)** путь A едет в прод — пишется полноценный UI.md с интеграцией; **(b)** путь A с оговоренными уступками — то же + список уступок в README; **(c)** натив не удовлетворяет — открывается разговор про WebView2, прототип остаётся как фолбэк. До вердикта никакой интеграции в основную программу.
